# Etapa 0.10 — esquema y autenticación de desarrollo

Rama Neon dev-saas. Managed Better Auth habilitado; Google compartido para pruebas; email/contraseña deshabilitado y alta por contraseña deshabilitada. Sin origen web público autorizado. No se modificó la rama principal.

El SQL neon/001-schema.sql define cuentas internas, planes, espacios, marcas, conexiones, archivos, borradores y cola privada. Las cuentas internas quedan deshabilitadas por defecto. El identificador auth_subject debe obtenerse exclusivamente de una sesión verificada de Neon Auth; no se acepta un identificador desde el navegador. No hay sincronización de usuarios automática ni FK a la tabla administrada de autenticación: la futura API debe verificar la existencia y el estado vigente de la identidad. La política de lectura se aplica mediante un rol NOLOGIN sin BYPASSRLS, usando faro.subject con set_config(..., true) dentro de una transacción del servidor. Nunca entregar una conexión SQL a clientes. El rol no puede escribir ni consultar la cola privada. El administrador de la base de datos conserva privilegios de mantenimiento y no debe ser el rol usado por la aplicación.

Siguiente fase: API autenticada, verificación de JWT y sesión, aprovisionamiento beta controlado, roles mínimos para escrituras, validación de cuotas y prueba del login real en un origen de desarrollo exclusivo. Las credenciales compartidas de Google no son de producción. No usar el origen compartido de GitHub Pages para sesiones reales. El sitio sigue como demo. No activar publicación automática. Los planes son propuestas, no suscripciones cobradas.
